# Ribosome f32 vs f64 precision sweep results

Generated by `min/ribosome/ribosome_precision_sweep.py`.

## What the harness does

```bash
python3 min/ribosome/ribosome_precision_sweep.py \
  --label hairpin --maxframe 2000 --seeds 20 --targets cpu,gpu --precisions f32,f64
```

It takes a base `.ergo` ribosome file, sweeps `SEED`, overrides `MAXFRAME`,
compiles and runs each variant under f32/f64 and CPU/GPU, then compares the
final-basin distributions and run times.

- f64 CPU and f64 GPU are bitwise-identical for these basin statistics.

Here `e_morse` is non-zero on GPU but grows away from the CPU value (CPU ~32,
GPU ~2 at frame 910). The GPU diagnostic kernels are not faithfully reproducing
the CPU diagnostic energies.

### Implication

The hairpin diagnostic energy mismatch was caused by missing GPU uploads before
a conditional block (`IF MC_EVERY > 0 ...`). The CPU wrote `RES_X/Y/Z`, but the
upload was placed inside the conditional branch, so it was skipped when the
condition was false, and the next GPU diagnostic kernel read stale device data.
A fix in `core/ir_codegen.py` now hoists the upload before the conditional.

The tRNA energy diagnostics still diverge from CPU. This is a separate issue:
the GPU trajectory itself diverges from the CPU trajectory (frames after ~100
show growing differences in `rgyr`, final structure, etc.). It is therefore not
merely a diagnostic readback bug, but a dynamics-level numerical difference in
the larger, more heavily offloaded tRNA simulation. Spot-checking other
systems shows this is a class-wide problem for any ribosome sim using the
unified packed pair-slot kernels (`PSEG`/`NSLOT`) or the frame-field orientation
coupling (`FRAME_K`/`FRAME_POS_K` > 0). It still needs to be root-caused before
GPU outputs from those systems can be trusted.

## Fix applied

- File: `core/ir_codegen.py`
- Function: `CCodeGen._emit_if()` and helper `_gpu_kernels_in_body()`.
- Change: when an `IRIf` contains GPU kernels (including kernels nested inside
  non-extracted loops), any CPU-dirty arrays those kernels read are uploaded to
  the GPU **before** the conditional branch is entered. This prevents the upload
  inside the branch from being skipped when the condition is false, which left
  the device copy stale and caused the next GPU kernel to read old data.
- Hairpin verification: f64 CPU and f64 GPU are now bitwise-identical for all
  reported columns across 5+ seeds.

## Scope of the GPU mismatch

I spot-checked other ribosome systems with a single-seed f64 CPU vs GPU run
(MAXFRAME=200, tolerance=1e-3):

| file | FRAME_K/FRAME_POS_K | PSEG/NSLOT | result |
|---|---|---|---|
| `rna_hairpin_0.0.ergo` | 0.0 / 0.0 | no | OK |
| `rna_hairpin_1.0.ergo` | 0.0 / 0.0 | no | OK |
| `rna_hairpin_2.0.ergo` | 0.0 / 0.0 | no | OK |
| `rna_trna_0.0.ergo` | 0.0 / 0.0 | no | OK |
| `rna_trna_1.0.ergo` | 0.0 / 0.0 | no | OK |
| `rna_trna_2.0.ergo` | 0.0 / 0.0 | no | OK |
| `rna_trna_phos_std_0.0.ergo` | 0.0 / 0.0 | no | OK |
| `rna_trna_stack_e025f01_0.0.ergo` | 0.1 / 0.1 | no | small mismatch (0.2–0.4%) |
| `rna5s_rnp_0.0.ergo` | 0.1 / 0.1 | no | large mismatch (e_morse 57%) |
| `oracle_phos_trim1_0.0.ergo` | 0.0 / 0.0 | no | e_morse only (0.3–1.3%) |
| `trna_gpu_0.ergo` | 0.1 / 0.1 | yes | large mismatch |
| `trna_gpu_1.ergo` | 0.1 / 0.1 | yes | large mismatch |
| `trna_gpu_2.ergo` | 0.1 / 0.1 | yes | large mismatch |
| `d5t_mono.ergo` | 0.1 / 0.1 | yes | large mismatch |
| `rnp_mono.ergo` | 0.1 / 0.1 | yes | large mismatch |
| `ul11_mono.ergo` | 0.1 / 0.1 | yes | large mismatch |
| `hmal_ul11_mono.ergo` | 0.1 / 0.1 | yes | large mismatch |

- **Simple systems** (FRAME_K = FRAME_POS_K = 0.0, no PSEG) match CPU/GPU.
- **Frame-field orientation coupling** (FRAME_K / FRAME_POS_K > 0) causes small but
  measurable numerical divergence, likely from f32 transcendentals in the GPU
  kernels.
- **Unified packed pair-slot systems** (PSEG/NSLOT) show much larger divergence
  and are the main source of the GPU-vs-CPU trajectory mismatch.
- `oracle_phos_trim1_0.0.ergo` is an outlier: no frame-field coupling, but the
  Morse reduction still disagrees slightly (grows to ~1.3% with more frames);
  this may be a separate reduction-precision issue.

So the GPU mismatch is **not limited to `trna_gpu_0.ergo`**; it is a class-wide
issue affecting the packed pair-slot (PSEG) GPU kernels and, to a lesser degree,
any system using the frame-field orientation coupling.

## Summary

- f64 GPU works end-to-end on the SPIR-V backend (tested on RTX 2060).
- Performance: ~7–9% slower on GPU under load, ~20–33% slower on CPU.
- Accuracy: f64 and f32 produce different but overlapping basin distributions;
  trajectory-level divergence is expected because of the precision-sensitive
  coil seeding.
- Determinism: within a single precision, CPU and GPU match for simple systems
  (hairpin, `rna_trna*`) with no frame-field coupling. For systems with
  FRAME_K/FRAME_POS_K > 0, and especially the packed pair-slot (PSEG) systems,
  GPU and CPU trajectories diverge.
- No NaNs observed in any f32 or f64 sweep.
- **Fixed**: hairpin GPU diagnostic energy (`e_morse`) now matches CPU.
- **Open issue**: GPU-vs-CPU divergence is a class-wide problem for PSEG pair-slot
  systems and frame-field-coupled systems, not just `trna_gpu_0.ergo`.

## Reproducibility

```bash
# Default small + medium sweep
python3 min/ribosome/ribosome_precision_sweep.py

# Heavy GPU-only sweep
python3 min/ribosome/ribosome_precision_sweep.py \
  min/ribosome/trna_gpu_0.ergo \
  --label trna_heavy --maxframe 5000 --seeds 8 \
  --targets gpu --precisions f32,f64

# Quick CPU vs GPU correctness check for any .ergo file
python3 min/ribosome/gpu_cpu_qcheck.py \
  min/ribosome/trna_gpu_0.ergo \
  min/ribosome/d5t_mono.ergo \
  --maxframe 200 --seeds 2
```

Outputs are written to `/tmp/ribosome_sweep/`.
